The FinCon Specification

Read the full specification before identifying causes and effects. This is the raw material for all subsequent stages.

📄 FinCon Overdraft Specification

FinCon: Overdraft Protection Rule

Scenario: FinCon applies the following rule for overdraft protection on payment processing:

  • If the account has overdraft protection enabled and the overdraft limit is not exceeded, a payment below the account balance is approved.
  • If the account has no overdraft protection and the balance is insufficient, the payment is rejected with INSUFFICIENT_FUNDS.
  • If the overdraft limit would be exceeded, reject with OVERDRAFT_LIMIT_EXCEEDED.
Rule 1: IF C1 (overdraft_enabled = true) AND C2 (limit_not_exceeded = true) AND C3 (payment_below_balance = true) THEN E1 (payment APPROVED) Rule 2: IF C1 = false (no overdraft protection) AND C3 = false (balance insufficient) THEN E2 (INSUFFICIENT_FUNDS) Rule 3: IF C2 = false (limit would be exceeded) THEN E3 (OVERDRAFT_LIMIT_EXCEEDED)

📋 Also: Pairwise Testing Question

A FinCon report export has three parameters:

Parameter Values format PDF / CSV / XML date_range last 7 days / last 30 days / custom include_cancelled yes / no

Full combination would require 3 × 3 × 2 = 18 test cases. Pairwise reduces this significantly.

Stage 2

Identifying the Causes

Causes are the input conditions that control the outcome. Scan for IF / WHEN / AND / OR keywords.

🔍 Step 1 — Understand the Spec

Use this trick to identify causes vs. effects:

IF / WHEN / PROVIDED THAT / AND / OR → Causes
THEN / RETURN / REJECT / APPROVE / MESSAGE → Effects

📥 Step 2 — The Three Causes

Scan the specification for input conditions (things that can be true or false).

1 Overdraft protection enabled? (Yes / No)
2 Overdraft limit not exceeded? (Yes / No)
3 Payment is below account balance? (Yes / No)

💡 These are causes because they determine the outcome. All are binary (1 = Yes, 0 = No).

Cause ID Description Values
C1 Overdraft protection enabled 1 = Yes, 0 = No
C2 Overdraft limit not exceeded 1 = Yes, 0 = No
C3 Payment is below account balance 1 = Yes, 0 = No
🎯

Rule: With 3 binary causes, you have a theoretical maximum of 2³ = 8 combinations. However, some combinations are impossible — reducing the actual test cases.

Stage 3

Identifying the Effects

Effects are the observable output results or system state changes. Look for THEN / RETURN / REJECT / APPROVE.

📤 The Three Effects

Look for the output results or system state changes in the specification.

1 Payment approved
2 Reject with INSUFFICIENT_FUNDS
3 Reject with OVERDRAFT_LIMIT_EXCEEDED

💡 These are effects because they are what happens as a result of the causes.

Effect ID Description Values
E1 Payment approved 1 = Yes, 0 = No
E2 Reject with INSUFFICIENT_FUNDS 1 = Yes, 0 = No
E3 Reject with OVERDRAFT_LIMIT_EXCEEDED 1 = Yes, 0 = No
💡 Teacher's Note

Effects must be mutually exclusive — exactly one effect fires per test case. If you find two effects firing simultaneously, re-check your cause identification.

Stage 4

The Decision Table

Each specification rule becomes one column — one complete test case. Rows = causes/effects, Columns = test cases.

📊 Build the Decision Table (Columns = Test Cases)

Each specification rule becomes one column — one complete test case.

Cause / Effect TC1 TC2 TC3
CAUSES C1 — Overdraft protection enabled 1 0 —
C2 — Overdraft limit not exceeded 1 — 0
C3 — Payment below account balance 1 0 —
EFFECTS E1 — APPROVED 1 0 0
E2 — INSUFFICIENT_FUNDS 0 1 0
E3 — OVERDRAFT_LIMIT_EXCEEDED 0 0 1

Each column represents one complete test case.

✅ Step 5 — Count the Test Cases

Number of test cases = 3 (TC1, TC2, TC3). Each column = one complete test case.

⚠️ Are There Impossible Combinations?

  • Yes. You cannot have C2 = 1 (limit not exceeded) and C2 = 0 (limit exceeded) simultaneously.
  • Some combinations are not defined by the specification — do not invent expected results for them.

🔑 Key Takeaways — Exam Formula

  • Causes = input conditions (IF WHAT?)
  • Effects = output/results (WHAT HAPPENS?)
  • Rows = causes/effects, Columns = test cases
  • Use constraints to remove impossible combinations
  • Each column = one complete test case

Q1 · PAIRWISE TESTING (4 P)

Source: CH03_Block_B_Pairwise_CEG.pdf

A FinCon report export has three parameters:

Parameter Values format PDF / CSV / XML date_range last 7 days / last 30 days / custom include_cancelled yes / no

(a) Explain what pairwise testing guarantees — and what it does NOT guarantee.

(b) Construct a pairwise test suite. How many test cases? Verify two specific pairs are covered.

👁️ Model Answer Click to reveal

(a) Guarantees (1 P):

  • Guarantees: Every possible combination of any two parameters (e.g., every format × every date_range) is covered by at least one test case.
  • Does NOT guarantee: 3-way interactions (e.g., PDF + custom + yes might miss a specific bug).

(b) Pairwise Test Suite (3 P):

Largest product: 3 × 3 = 9 (format × date_range) → minimum 9 test cases.

TC Format Date_Range Include_Cancelled 1 PDF 7 days yes 2 PDF 30 days no 3 PDF custom yes 4 CSV 7 days no 5 CSV 30 days yes 6 CSV custom no 7 XML 7 days yes 8 XML 30 days no 9 XML custom yes

Verification: CSV + yes → TC5 ✓ | XML + 30 days → TC8 ✓
