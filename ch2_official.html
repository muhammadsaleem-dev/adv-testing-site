🏛️ Official Q EC METHOD (3 P)

Source: AdvTest_03_EC_BVA.pdf

The FinCon login form accepts a PIN: a 4-digit numeric string (e.g., "1234").

Perform the following tasks:

  • (a) Define a complete set of equivalence classes for the PIN input.
  • (b) For each class, state one representative value and the expected system response.

Suggested Answer:

(a) Complete set of equivalence classes (1.5 P):

To fully partition the input space, we need one valid class and all corresponding invalid classes.

  • Valid EC: Exactly 4 digits (numeric string).
  • Invalid EC 1: String length < 4 (too short).
  • Invalid EC 2: String length > 4 (too long).
  • Invalid EC 3: String containing non-numeric characters (letters, symbols, whitespace).
  • Invalid EC 4: Empty string.

(b) Representative values and expected responses (1.5 P):

  • Valid EC: "1234" → Accepted / processed.
  • Invalid EC 1: "12" → Rejected / error message.
  • Invalid EC 2: "12345" → Rejected / error message.
  • Invalid EC 3: "12A4" → Rejected / error message.
  • Invalid EC 4: "" → Rejected / error message.

Examiner note: Award full credit if at least three distinct invalid equivalence classes are identified alongside the valid class, with correct expected behaviour mapping.

🏛️ Official Q BOUNDARY VALUE ANALYSIS (4 P)

Source: AdvTest_03_EC_BVA.pdf

A FinCon savings account pays a bonus interest rate of 1.5% on the balance above €10000.

The interest is calculated as:

if balance > 10000: interest = (balance - 10000) * 0.015 else: interest = 0

Perform the following tasks:

  • (a) List all boundary values for balance that must be tested.
  • (b) For each boundary value, state the expected value of interest.
  • (c) A colleague proposes testing only balance = 5000 and balance = 15000. What is the critical risk of this approach?

Suggested Answer:

(a) Boundary values to test (1.5 P):

According to Boundary Value Analysis principles, we must test just below, exactly at, and just above the boundary condition (10000). Assuming standard currency representation (cents/decimals) or integers:

  • Just below: 9999.99 (or 9999)
  • Exactly at: 10000.00 (or 10000)
  • Just above: 10000.01 (or 10001)

(b) Expected value of interest (1.5 P):

  • For 9999.99: expected interest = 0 (condition > 10000 is false).
  • For 10000.00: expected interest = 0 (condition > 10000 is false).
  • For 10000.01: expected interest > 0 (specifically: 0.00015, condition is true).

(c) Critical risk of this approach (1 P):

Testing only values deep inside the equivalence partitions (5000 and 15000) completely misses boundary defects. The most common programming errors are off-by-one errors (e.g., using >= instead of >). A test suite with only 5000 and 15000 will silently pass even if the code incorrectly uses balance >= 10000, meaning a user with exactly 10000 would incorrectly receive a bonus.

🏛️ Official Q MULTI-DIMENSIONAL TEST DATA (3 P)

Source: AdvTest_03_EC_BVA.pdf

A FinCon money transfer has two independent inputs:

  • amount (1–100000 EUR cents)
  • target_account (must exist in the system: boolean).

A tester builds this test suite:

TC amount target_account Expected 1 500 True approved 2 0 False rejected 3 200000 False rejected

Identify two structural problems with this test suite; propose one additional test case that addresses them.

Suggested Answer:

(a) Two structural problems (2 P):

  • Problem 1 — Multiple invalid conditions combined: Test Cases 2 and 3 combine an invalid amount with an invalid target_account. If the system rejects the transaction, it is impossible to know which of the two invalid inputs triggered the rejection (this is known as fault masking).
  • Problem 2 — Missing isolation combinations: The multi-dimensional strategy states that we must combine every invalid class of one parameter with valid classes of all others. This suite completely fails to test the combination of a valid amount with an invalid target_account, or an invalid amount with a valid target_account.

(b) Additional test case (1 P):

To isolate the failure, we must combine an invalid class of one parameter with valid classes of all others. Any of the following test cases address this:

  • TC 4: amount = 500 (valid), target_account = False (invalid) → Expected: rejected
  • TC 5: amount = 0 (invalid), target_account = True (valid) → Expected: rejected
