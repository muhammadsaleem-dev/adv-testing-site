Key concepts and techniques

🎯 Chapter 1 Core Mission: From Intuitive Guesswork to Systematic Evidence

Software testing is not merely "running the app to see if it crashes." It is a controlled information process designed to reduce risk and uncertainty:
Uncertainty → Empirical Evidence → Confident Release Decision.

1. The Myers Triangle Problem: Why Testing is Deceptively Hard

In 1979, software engineering pioneer Glenford Myers introduced a deceptively simple programming task that remains the ultimate baseline for test case completeness.

The Specification:

"The program accepts three integer values representing the lengths of the sides of a triangle (a, b, c). It returns a string stating whether the triangle is scalene, isosceles, or equilateral."

Most untrained developers write only 3 test cases (one for each word). However, to be rigorously tested, Myers showed that at least 14 distinct test categories are required:

🎓 Essential Exam Takeaway:

Never assume a program works because it handles happy paths. Even a 5-line script has boundary conditions, geometric constraints (triangle inequality theorem a + b > c), and invalid input types. Testing adds business value by systematically probing these hidden failure modes.

2. The Anatomy of a Complete Test Case

In professional testing, writing "test with amount=500" is incomplete and unexecutable. A standardized test case requires 4 pillars:

1. Preconditions

The exact environmental state required before execution (e.g. "User is logged in; source account has balance ≥ €500").

2. Explicit Input & Action

The exact, reproducible values entered and specific trigger executed (e.g. "Enter amount = 500 cents, click 'Confirm Transfer'").

3. Expected Result (Oracle)

The concrete, measurable output expected from a correct system (e.g. "Return 'approved'; HTTP status 200").

4. Postconditions

The resulting system state after the action finishes (e.g. "Balance debited by €5.00; immutable audit log record created").

3. ISTQB 4.0 Core Terminology & Causation Chain

One of the most heavily graded exam topics is distinguishing between Error, Defect, and Failure:

Human Action
→ leads to →
💻 DEFECT (Bug / Fault)
Flaw in Code or Spec
→ causes →
💥 FAILURE
Runtime Deviation
ISTQB Term Precise Definition FinCon Example
Error (Mistake) A human action (misunderstanding, fatigue, typo) that produces an incorrect result. A developer copies a fee-deduction line twice while editing the transfer module.
Defect (Bug, Fault) A static flaw or anomaly in a component, code, or requirement document. The duplicate fee deduction code remains committed in the repository.
Failure An observable runtime deviation of the software from its expected behavior or output. A customer executes a €100 transfer and notices €10 deducted instead of €5.
Root Cause The fundamental, underlying reason for a defect. Removing it prevents an entire class of defects. Lack of code reviews and missing automated static analysis linters in the CI/CD pipeline.
Testing vs. Debugging Testing: Demonstrates quality and finds failures against the spec.
Debugging: Locates, analyzes, and fixes root causes in code.		 Testing: Automated pytest marks transfer test red.
Debugging: Developer attaches debugger and removes duplicate line.
Error Masking A condition where two distinct defects compensate for each other, hiding external failures during runtime execution. One function adds €5 extra fee, but the display function subtracts €5 erroneously → balance appears correct while ledger is corrupted!

4. AI in Testing: Capabilities, Traps & The Evolved Role

The emergence of LLMs (ChatGPT, Copilot) has transformed software engineering. In the exam, the professor specifically tests your ability to critique AI test outputs.

✨ What AI Does Exceptionally Well:

  • Rapid Test Drafting: Generates initial test suites and boilerplate pytest/doctest fixtures in seconds.
  • Test Data Synthesis: Synthesizes large arrays of diverse names, addresses, and sample currencies.
  • Defect Triage & Summarization: Clusters bug reports and suggests potential duplicate issues.

⚠️ Critical AI Traps & Risks:

  • Hallucinations: LLMs generate plausible-looking test cases with completely fabricated assertions.
  • Happy-Path Bias: AI defaults to standard cases and systematically omits tricky boundaries.
  • The Circular Oracle Trap: AI prompted with buggy code will write test assertions that match the bug!
  • Automation Bias: Human testers blindly trusting green AI test results without reviewing logic.

The Shift in the Tester's Role

Routine manual test execution is increasingly automated. The modern test engineer shifts to the role of Validator, Specification Guardian, and Prompt Architect. Senior testers formulate precise constraints, verify AI-generated assertions against legal/business specs, and identify the blind spots AI cannot see.

5. Python Doctest Engineering for Testers

In this course, Python Doctests bridge documentation and automated unit verification by embedding interactive test sessions directly inside Python docstrings.

Complete Doctest Implementation (FinCon Triangle Classifier):

def classify_triangle(a: int, b: int, c: int) -> str: """ Classifies a triangle based on three integer side lengths. Valid Equilateral, Isosceles & Scalene: >>> classify_triangle(5, 5, 5) 'equilateral' >>> classify_triangle(3, 3, 4) 'isosceles' >>> classify_triangle(3, 4, 3) 'isosceles' >>> classify_triangle(3, 4, 5) 'scalene' Invalid & Degenerate inputs (Must raise ValueError): >>> classify_triangle(0, 0, 0) Traceback (most recent call last): ... ValueError: sides must be positive integers >>> classify_triangle(1, 2, 3) Traceback (most recent call last): ... ValueError: not a valid triangle (triangle inequality violation) """ # 1. Guard: Check for non-positive sides if a <= 0 or b <= 0 or c <= 0: raise ValueError("sides must be positive integers") # 2. Guard: Check triangle inequality theorem (sum of any 2 > 3rd) if (a + b <= c) or (a + c <= b) or (b + c <= a): raise ValueError("not a valid triangle (triangle inequality violation)") # 3. Classify valid triangles if a == b == c: return "equilateral" elif a == b or a == c or b == c: return "isosceles" else: return "scalene"

Running Doctests from Command Line:

python -m doctest -v triangle_classifier.py
💡 Doctest Exception Formatting Rule:

When asserting that an exception is raised in a doctest, you only write Traceback (most recent call last):, followed by the wildcard ellipsis ..., and then the exact exception line (e.g. ValueError: sides must be positive integers).
