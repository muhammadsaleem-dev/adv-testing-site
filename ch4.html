4. White-Box Coverage & MC/DC

Key concepts and techniques

Coverage tells you what code was executed. It does not prove that the behaviour was correct.

Black-box versus white-box

AspectBlack-boxWhite-box
BasisSpecificationSource-code structure
FindsMissing/wrong behaviourUntested branches, dead code
RiskMay miss structural gapsMay miss missing requirements

Coverage hierarchy

CriterionQuestionMain limitation
StatementDid every executable statement run?Can miss false outcomes and ignored parameters.
Branch/decisionDid every decision take true and false outcomes?Does not prove each condition matters independently.
ConditionWas every atomic condition true and false?Different conditions can be masked.
MC/DCDid each condition independently change the decision?More expensive; used for safety-critical logic.
Subsumption used in this course: Statement < Branch < Condition < MC/DC. Higher criteria provide stronger structural evidence. But no structural criterion replaces a correct oracle.

MC/DC rule

For each condition, find two tests where only that condition changes and the overall decision also changes. For the simple course examples, n conditions often need a minimum of n+1 tests.

unittest and AAA

class TestBankAccount(unittest.TestCase):
    def test_deposit_increases_balance(self):
        # Arrange
        account = BankAccount('Alice', 1000.0)
        # Act
        account.deposit(500.0)
        # Assert
        self.assertEqual(account.balance, 1500.0)

Mocks

  • Mocks replace slow, fragile, destructive or non-deterministic dependencies.
  • Configure return values, run the SUT, assert the result, then verify interactions.
  • Also verify methods that must not be called.
Mocking trap: A test that only checks the return value can miss wrong side effects. A test that only checks calls can miss a wrong return value. Check both when both are part of the contract.

Worked exam questions

✏️ Transfer coverage count (3 marks) (Source) A function returns invalid, unknown_target, limit_exceeded or approved through sequential early returns. How many tests for statement and branch coverage?

Four tests are needed for both, because each return statement/path is mutually exclusive: invalid amount; missing target; amount above limit; approved. A claim of 100% statement coverage while never executing the limit_exceeded return is inconsistent. Even with 100% coverage, the expected results may still be wrong.

✏️ MC/DC with P and (B or O) (4 marks) Construct a minimum suite for P AND (B OR O).

Use four tests: T,T,F -> T; F,T,F -> F (P independence); T,F,F -> F (B independence compared with first); T,F,T -> T (O independence compared with third). Condition coverage alone can make every condition true/false without proving independent influence.

✏️ Mock transfer (4 marks) Happy path should debit sender, credit recipient and email recipient.

Create MagicMock objects; configure db.find_account to return a recipient with an email; call send_transfer; assert “transfer_complete”; assert debit_sender(amount), credit_recipient(recipient, amount), and send_email(email, amount) once. For None recipient, assert “recipient_not_found” and assert both debit and credit were not called.
