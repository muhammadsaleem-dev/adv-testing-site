4. White-Box Coverage & MC/DC

Key concepts and techniques

🎯 Chapter 4 Core Mission: White-Box Coverage Hierarchy & Mock Isolation

White-box testing measures structural execution of code. Master the coverage hierarchy from Statement Coverage up to MC/DC (Modified Condition/Decision Coverage), and learn how to isolate side-effects using Python Mocks.

1. The White-Box Coverage Hierarchy & Subsumption

A coverage criterion A subsumes criterion B if achieving 100% coverage in A mathematically guarantees 100% coverage in B:

Statement (Weakest) → subsumed by → Branch (Decision) → subsumed by → MC/DC → subsumed by → Multiple Condition / Path (Strongest)

⚠️ Classic Exam Trap: Statement vs. Branch Coverage

Statement Coverage does NOT subsume Branch Coverage!
Consider an if (condition) { do_something(); } without an else block. A single test where condition = True achieves 100% Statement Coverage, but only 50% Branch Coverage because the False evaluation path was never tested!

2. MC/DC (Modified Condition/Decision Coverage)

Mandated in safety-critical systems (such as aviation standard DO-178C and automotive ISO 26262), MC/DC proves that each individual boolean condition can independently affect the overall decision outcome.

📐 The MC/DC Test Count Rule:

For a decision with N independent boolean conditions, full Multiple Condition Coverage requires 2N test cases (exponential explosion).
MC/DC requires exactly N + 1 test cases to demonstrate independent effect for all N conditions!

MC/DC Truth Table Walkthrough:

Rule: is_premium and (balance > 10000 or overdraft_enabled) → Expression: P ∧ (B ∨ O)

TC # P (Premium) B (Balance > 10k) O (Overdraft) Decision Output Independence Pair Role
TC1 T T F TRUE Baseline for B (with TC3) and P (with TC4)
TC2 T F T TRUE Baseline for O (with TC3)
TC3 T F F FALSE Proves B toggles output (TC1 vs TC3) & O toggles (TC2 vs TC3)
TC4 F T F FALSE Proves P toggles output (TC1 vs TC4)

3. Unit Isolation with Python Mocks

In unit testing, we test code in isolation from external databases, networks, and payment APIs. We use unittest.mock.MagicMock to verify that dependencies are called correctly — or never called on negative paths!

from unittest.mock import MagicMock def test_transfer_rejection_does_not_call_notifier(): mock_db = MagicMock() mock_notifier = MagicMock() # Simulate non-existent account in database mock_db.find_account.return_value = None result = send_transfer(amount=500, recipient_id="acc_999", db=mock_db, notifier=mock_notifier) # Assert return value assert result == "rejected" # CRITICAL: Verify notifier was NOT invoked on failure path! mock_notifier.send.assert_not_called()
