3. Pairwise & Decision Tables

Key concepts and techniques

🎯 Chapter 3: Pairwise Testing & Cause-Effect Graphing

Directly aligned with lecture slides (CH03_Block_B_Pairwise_CEG.pdf).

1. When EC + BVA is Not Enough (Slides 6–7)

Equivalence classes and boundary values test each parameter in isolation.
But bugs also hide in interactions between parameters:

"Would you expect the autopilot to switch off if the toilet is flushed?"

• Two independently valid inputs combine to produce an unexpected failure.
• EC and BVA will miss this entirely!

The Full-Combination Problem (Slide 7)

  • For a FinCon transaction form with 4 independent parameters, each with 3 values:
    3 × 3 × 3 × 3 = 81 test cases
  • For a configuration screen with 10 parameters at 3 values each:
    310 = 59,049 test cases
  • Conclusion: Full combination testing is completely impractical.

2. Pairwise Testing (Slide 8)

🔑 Key Insight:

Most bugs are triggered by the interaction of two parameters, not three or more.
The Rule: Test every pair of parameter values at least once — instead of every full combination.
Result: Typically reduces the test set by 80–95% while retaining high defect-finding power for two-way interactions.

3. Pairwise: How It Works & Minimum Table (Slides 9–11)

Given Parameters:

Parameter Values
Print Header Checked / Unchecked (2 values)
Print Logo Yes / No (2 values)
Print Footer Checked / Unchecked (2 values)
Print Date Today / Last saved / Special date (3 values)

• Full combinations: 2 × 2 × 2 × 3 = 24 test cases.
• Pairwise Requirement: Every combination of values between any two parameters must appear at least once.
• The Largest 2-way pair is: Header (2) × Date (3) = 2 × 3 = 6 test cases.
• Therefore, fewer than 6 test cases cannot be sufficient.

The Exact 6-Row Minimum Table (Slide 10)

TC # Header Logo Footer Date
1 Checked Yes Checked Today
2 Checked No Unchecked Last saved
3 Checked Yes Unchecked Special date
4 Unchecked No Checked Today
5 Unchecked Yes Unchecked Last saved
6 Unchecked No Checked Special date

"This table covers every 2-way pair at least once. Other 6-row tables are valid if they cover the same pairwise combinations." (Slide 10–11)

4. Pairwise Applied to FinCon (Slides 13–14)

The FinCon transfer form has four independent parameters:

Parameter Values
amount small (500) / boundary (100000) / oversized (200000) → 3 values
currency EUR / USD / invalid → 3 values
target_account_exists yes / no → 2 values
session_valid yes / no → 2 values

5-Minute Slide Exercise Answer:

• Full combinations: 3 × 3 × 2 × 2 = 36 test cases.
• Expected Pairwise Minimum: The two largest parameters are amount (3) × currency (3) = 9 test cases!
• Most important 2-way interaction: amount × currency (financial validity logic).

5. Cause-Effect Graphing (CEG) & Notation (Slides 16–20)

Both EC and BVA test individual parameters independently.
Neither systematically tests combinations that arise from logical dependencies in the specification:

"The file is updated if column 1 is A or B and column 2 is a digit."

The 7-Step Process (Slide 18)

  1. Divide the specification into workable pieces (one graph per feature/rule).
  2. Identify Causes — distinct input conditions or equivalence classes.
  3. Identify Effects — output conditions or system state changes.
  4. Draw the Boolean graph linking causes to effects.
  5. Add Constraints for impossible combinations.
  6. Convert the graph to a Decision Table — each column is one test case.
  7. Each column becomes a test case.

Notation: Boolean Symbols (Slide 19)

Symbol Meaning
Identity If A = 1, then B = 1
NOT If A = 1, then B = 0
AND C = 1 only if A = 1 and B = 1
OR C = 1 if A = 1 or B = 1 (or both)

Constraints Between Causes (Slide 20)

Constraint Rule Meaning
E (Exclusive) At most one can be true. Both cannot be 1 at the same time.
I (Inclusive) At least one must be true. Both cannot be 0 at the same time.
O (One & Only One) Exactly one is true. (1 and only 1).
R (Requires) For A to be 1, B must be 1. (A requires B).
M (Masks - Effects) If Effect 1 is true, Effect 2 is suppressed/masked.

6. Classic Example — Character Validation (Slides 30–31)

Specification:

  • The character in column 1 must be "A" or "B".
  • The character in column 2 must be a digit.
  • If both are valid, the file is updated.
  • If column 1 is invalid, message X12 is issued.
  • If column 2 is not a digit, message X13 is issued.
Causes:
  • C1: column 1 = "A"
  • C2: column 1 = "B"
  • C3: column 2 = digit
Effects:
  • E70: file updated
  • E71: message X12 issued
  • E72: message X13 issued

Constraints: An E (Exclusive) constraint exists between C1 and C2 (Column 1 cannot be both "A" and "B" simultaneously).

Resulting Decision Table (4 Test Cases)

Condition / Action TC 1 TC 2 TC 3 TC 4
C1: col 1 = 'A' 1 0 0 1
C2: col 1 = 'B' 0 1 0 0
C3: col 2 = digit 1 1 1 0
E70: File Updated X X — —
E71: Msg X12 (col 1 invalid) — — X —
E72: Msg X13 (col 2 not digit) — — — X
