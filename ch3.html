3. Pairwise & Decision Tables

Key concepts and techniques

🎯 Chapter 3: Pairwise Testing & Cause-Effect Graphing

The 3-minute crystal-clear guide. Learn why testing all combinations is impossible, how the 2-Friend Fight Analogy slashes tests by 90%, and master the 5-Second Exam Shortcut!

1. The Problem: Why We Cannot Test Everything

Imagine testing a Flight Booking Form with 4 simple dropdowns:

  • Class: Economy, Business, First (3 choices)
  • Payment: Credit Card, PayPal, Crypto (3 choices)
  • Seat: Window, Aisle, Middle (3 choices)
  • Meal: Standard, Vegetarian, Halal (3 choices)

To test every single combination, you need:
3 × 3 × 3 × 3 = 81 test cases!

Now imagine a real app with 10 settings (3 choices each):
310 = 59,049 test cases! (Completely impossible to test manually).

2. The Breakthrough: How Real Bugs Actually Happen

💡 The 2-Friend Fight Analogy

Imagine a party with 4 friends. Bugs in software rarely happen because 4 complicated things went wrong at once. Bugs almost always happen because two specific settings hate each other!

✈️ The Professor's Airplane Analogy:

"Would you expect the autopilot to switch off if the toilet is flushed?"

• Testing toilet alone → Works ✅
• Testing autopilot alone → Works ✅
• Testing toilet + autopilot together → 💥 Crash!

🎯 The Golden Rule of Pairwise Testing:

"Make sure every possible PAIR of 2 values meets in the same test case AT LEAST ONCE."

Over 80% of all software defects are 2-way interactions. By testing every pair of two, you slash test cases by 80–95% while catching almost all bugs!

3. The 5-Second Exam Math Shortcut

On the exam, the professor gives you a list of settings and asks:
"What is the absolute minimum number of test cases required for Pairwise coverage?"

📐 The 5-Second Trick:

Find the two largest numbers in the parameter list and multiply them:

Pairwise Minimum ≥ (Largest Parameter Values) × (2nd Largest Parameter Values)
Example A: Print Dialog
  • Date: 3 choices
  • Header: 2 choices
  • Logo: 2 choices
  • Footer: 2 choices

• Full: 3 × 2 × 2 × 2 = 24 tests
• Pairwise Min: 3 × 2 = 6 tests!

Example B: FinCon Transfer
  • Amount: 3 choices
  • Currency: 3 choices
  • Target Exists: 2 choices
  • Session Valid: 2 choices

• Full: 3 × 3 × 2 × 2 = 36 tests
• Pairwise Min: 3 × 3 = 9 tests!

4. How the Table is Built (The 3-Step "Outfit" Game)

How do automated tools build a 6-row table that covers every pair? Think of picking a daily outfit:
• Shoes: Boots, Sneakers, Sandals (3 choices)
• Shirt: Red, Blue (2 choices)
• Pants: Jeans, Shorts (2 choices)

Since Shoes (3) × Shirt (2) = 6, we need 6 rows:

Step Shoes (Largest - 3) Shirt (2 choices) Pants (2 choices)
Row 1 Boots Red Jeans
Row 2 Sneakers Red Shorts
Row 3 Sandals Red Jeans
Row 4 Boots Blue Shorts
Row 5 Sneakers Blue Jeans
Row 6 Sandals Blue Shorts
✅ Look at the coverage:
• Red met all 3 shoes, Blue met all 3 shoes.
• Jeans met all 3 shoes, Shorts met all 3 shoes.
• Every Shirt met both Pants!
In just 6 tests, 100% of all pairs are tested!

5. Cause-Effect Graphing (CEG) & Decision Tables

What if settings depend on complex business rules? Cause-Effect Graphing turns rules into a simple Decision Table (where each vertical column is 1 test case).

The 4 Exam Constraint Letters (Crucial for Exam!)

Sometimes certain input combinations are physically impossible in real life. We mark these with 4 letters:

🍕 The Restaurant Analogy: "Can You Pick BOTH?"

  • I (Inclusive = "At least ONE"): "Choose sauce: Ketchup or Mayo."
    → You can pick Ketchup, you can pick Mayo, or you can pick BOTH (Ketchup + Mayo)! You just cannot pick zero.
  • O (One & Only One = "Exactly ONE"): "Pick drink size: Small or Large."
    → You must pick strictly ONE. You cannot pick both sizes for 1 cup, and you cannot pick zero!
  • E (Exclusive = "At most ONE"): "Pick a free bonus: Cookie or Apple."
    → You can pick zero (0), or you can pick one (1), but you cannot pick BOTH!
  • R (Requires = "A needs B"): "To Checkout, you REQUIRE items in your cart."
    → If Action A is true, Condition B must also be true (A → B).

📊 The 10-Second Allowed Combinations Summary:

If you pick... I (Inclusive) O (One & Only One) E (Exclusive)
Pick ZERO (0) ❌ Forbidden ❌ Forbidden ✅ Allowed (0 or 1)
Pick ONE (1) ✅ Allowed ✅ Allowed (Strictly 1) ✅ Allowed (0 or 1)
Pick BOTH (2) ✅ ALLOWED! ❌ Forbidden ❌ Forbidden

Example 1: The Intuitive Login Screen Decision Table

Think of an app login screen with Username and Password:
• 1 = TRUE / Correct input.
• 0 = FALSE / Wrong input.
• X = Action happens (Output triggered).
• — = Action does not happen.

Conditions & Actions TC 1 (Success) TC 2 (Wrong Pass) TC 3 (Wrong User) TC 4 (Both Wrong)
C1: Username Correct? 1 1 0 0
C2: Password Correct? 1 0 1 0
E1: Action: Unlock Account X — — —
E2: Action: Show Error Message — X X X

Example 2: The Professor's Official Slide Example (Character Validation - Slides 30–31)

Official Specification:

  • Column 1 must be "A" or "B".
  • Column 2 must be a digit.
  • If both are valid → File is updated ($E_{70}$).
  • If Column 1 is invalid → Message X12 is issued ($E_{71}$).
  • If Column 2 is not a digit → Message X13 is issued ($E_{72}$).

• Causes: C1 (Col 1 = 'A'), C2 (Col 1 = 'B'), C3 (Col 2 = digit).
• Constraint: E (Exclusive) between C1 and C2 (Column 1 cannot be 'A' and 'B' at the same time!).

Condition / Action TC 1 (Happy A) TC 2 (Happy B) TC 3 (Col 1 Fail) TC 4 (Col 2 Fail)
C1: col 1 = 'A' 1 0 0 1
C2: col 1 = 'B' 0 1 0 0
C3: col 2 = digit 1 1 1 0
E70: File Updated X X — —
E71: Msg X12 (Col 1 error) — — X —
E72: Msg X13 (Col 2 error) — — — X
