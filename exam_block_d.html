Topic The Exact Structure Demanded

Scenario: FinCon Beneficiary Management

FinCon introduces beneficiary management.
The system must validate account data, user session, confirmation, and audit trail.

D1) List three important risks. For each, estimate priority and define a test response. (6 P)

Instructions: Identify 3 distinct failure modes across data, session, confirmation, or audit trail. Specify priority (Exposure) and the concrete test response.

👁️ Model Answer & Rubric Click to reveal D1 solution
Risk Priority Test response
1. Unauthorized beneficiary creation via expired or hijacked session / CSRF (attacker adds unauthorized recipient). High
(Critical Impact)		 Security & Negative Integration Tests: Attempt adding beneficiary with expired token, manipulated session ID, and missing CSRF headers.
2. Invalid or malformed account data accepted (e.g., incorrect IBAN checksum, invalid length), leading to failed/misrouted transfers. High
(High Probability)		 Equivalence Partitioning & BVA: Test valid IBANs, invalid MOD-97 checksums, min/max length boundaries, and non-alphanumeric input.
3. Confirmation / 2FA bypass allowing beneficiary persistence without secondary authentication. High
(High Impact)		 Negative Workflow Tests: Submit beneficiary payload while skipping confirmation step or supplying invalid 2FA/TAN code.

Alternative valid risk: Missing audit trail on beneficiary creation/modification (Priority: Medium-High → Test response: Integration test asserting DB audit log records).

D2) Define two entry criteria and two exit criteria for testing this feature. (6 P)

Instructions: Provide objective, reviewable quality gates. Avoid vague phrases like "software is ready".

👁️ Model Answer & Rubric Click to reveal D2 solution
📋 Entry criteria 🚩 Exit criteria
1. Unit tests for account validation pass with ≥ 90% branch coverage in the CI/CD pipeline. 1. 100% of P1/P2 test cases executed with a 100% pass rate on all critical security & financial flows.
2. Test environment deployed with mock banking API and test accounts provisioned. 2. Zero open Critical or High severity defects (no blockers in session, confirmation, or validation).

D3) Select two suitable test levels and justify what each level should verify. (6 P)

Instructions: Choose from standard ISTQB test levels (Unit, Integration, System, Acceptance) and provide specific justifications for Beneficiary Management.

👁️ Model Answer & Rubric Click to reveal D3 solution
🧱 Test level 🔍 What it verifies 💡 Why suitable
1. Unit / Component Testing Account data validation algorithms: IBAN MOD-97 checksum calculation, regex patterns, field length boundaries, and string sanitization. Fast, deterministic, and exhaustive: Provides high combinatorial coverage of invalid input classes in isolation without requiring database/network overhead.
2. System / Integration Testing (End-to-End) Complete workflow: User login → Session validation → Beneficiary input → 2FA confirmation prompt → DB persistence → Audit trail logging. Verifies cross-boundary integrity: Ensures authentication, multi-step confirmation, and immutable audit logging work reliably together across services.

D4) Name two decision-oriented test metrics and one misleading metric. Explain in brief. (7 P)

Instructions: Connect metrics to stakeholder decision questions vs. raw vanity/activity counts.

👁️ Model Answer & Rubric Click to reveal D4 solution
  • Decision-oriented metric 1: Open High-Severity Defect Count / Density by Risk Area (e.g., number of open defects in security, session, or confirmation).
  • Decision-oriented metric 2: Pass Rate of Critical (P1) Acceptance / Business Scenarios (percentage of mandatory regulatory & core financial checks currently green).
  • Misleading metric: Total Number of Executed Test Cases (or total test count / lines of test code).
  • Explanation: Decision-oriented metrics directly answer release-risk questions (e.g. "Is financial and customer data safe to deploy?"). In contrast, total test count measures only activity or volume, not quality or risk reduction — 1,000 passing low-risk UI tests give a dangerous illusion of quality if the single critical 2FA confirmation test is failing or omitted.
