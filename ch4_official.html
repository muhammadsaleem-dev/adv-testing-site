Stage 1

The Coverage Subsumption Hierarchy

Understanding which coverage criteria mathematically include and guarantee others — and why Statement coverage alone is dangerously deceptive.

The Coverage Hierarchy Ladder

Coverage criterion A subsumes B if every test suite that satisfies A is mathematically guaranteed to also satisfy B.

Multiple Condition Coverage / Path Coverage STRONGEST (often 2ⁿ tests)
▼ subsumes
MC/DC (Modified Condition / Decision Coverage) N + 1 TESTS (Aviation DO-178C)
▼ subsumes
Branch / Decision Coverage Every branch True AND False
▼ subsumes
Statement Coverage WEAKEST (Lines executed)
Official Exam Task 1

The Guard Clause Transfer Code

def transfer(amount: float, target_exists: bool, daily_limit: float) -> str: if amount <= 0: return "invalid" if not target_exists: return "unknown_target" if amount > daily_limit: return "limit_exceeded" return "approved"
(a) 100% Statement Coverage
4 Test Cases

Each return statement is mutually exclusive. To execute all 4 return statements, you need exactly 4 test cases.

(b) 100% Branch Coverage
4 Test Cases

Because all branches are early-exit guard clauses, the 4 tests that trigger the 3 True paths + 1 final False fall-through naturally cover 100% of branches.

🎯 Exam Gotcha (Part c): A colleague claims they achieved 100% statement coverage but missed limit_exceeded. In this specific code, that is mathematically impossible because return "limit_exceeded" is itself an executable statement! If they skipped that line, their statement coverage was not 100%. General takeaway: In non-guard code (where status flags are overwritten), statement coverage routinely misses entire logic branches.
Stage 2

MC/DC: The Aviation Safety Standard

Why aviation standard DO-178C mandates MC/DC, how the N+1 formula works, and how to verify condition independence in seconds.

"Each condition has been shown to independently affect the decision outcome by varying just that condition while holding all other possible conditions fixed." — FAA RTCA DO-178C (Level A Aviation Standard)

Rule 1: The Size Formula (N + 1)

Instead of testing all $2^N$ combinations (which explodes exponentially), MC/DC achieves rigorous safety with a linear minimum of N + 1 test cases for $N$ conditions.

N=2 conditions → Min 3 tests
N=3 conditions → Min 4 tests
N=4 conditions → Min 5 tests

Rule 2: The Independence Pair

To prove condition $X$ is independently influential, you must locate two test cases $(TC_a, TC_b)$ where:

  • Condition $X$ flips ($0 \leftrightarrow 1$)
  • All other conditions remain identical
  • The final decision outcome flips

⚠️ Why Condition Coverage Alone Fails

Condition Coverage only demands that every sub-condition evaluates to True and False at least once. It does not check whether that condition actually reached the final output or was masked by short-circuit operators. MC/DC proves the condition has real control.

Stage 3

The FinCon MC/DC Decision Table

Step-by-step construction of the official 4-point exam question with full truth values and independence pair verification.

FinCon Bonus Rule
if is_premium and (balance > 10000 or overdraft_enabled):
    apply_bonus_rate()

Variables: $P = \text{is\_premium}$, $B = (\text{balance} > 10000)$, $O = \text{overdraft\_enabled}$.
Formula: $\text{Decision} = P \text{ and } (B \text{ or } O)$.

Test Case P (Premium) B (Balance > 10k) O (Overdraft) (B or O) Decision Outcome
TC1 True True False True True (Bonus Applied)
TC2 False True False True False (No Bonus)
TC3 True False False False False (No Bonus)
TC4 True False True True True (Bonus Applied)

Independence Proof Verification:

Proving Independence of P: Pair TC1 & TC2

P flips (T→F). B is held at True, O is held at False. Outcome flips from True to False. ✅

Proving Independence of B: Pair TC1 & TC3

B flips (T→F). P is held at True, O is held at False. Outcome flips from True to False. ✅

Proving Independence of O: Pair TC3 & TC4

O flips (F→T). P is held at True, B is held at False. Outcome flips from False to True. ✅

Python Mocking (`unittest.mock`)

Testing unit functions in complete isolation using MagicMock: verifying side-effect calls, return values, and non-interactions.

Target Function Under Test
def send_transfer(amount: int, recipient_id: str, db, notifier) -> str: recipient = db.find_account(recipient_id) if recipient is None: return "recipient_not_found" db.debit_sender(amount) db.credit_recipient(recipient, amount) notifier.send_email(recipient.email, amount) return "transfer_complete"

Task (a): Happy Path Test (2 Points)

Assert Called

Verifies that when the recipient exists, debit_sender, credit_recipient, and notifier.send_email are executed with the exact expected arguments.

from unittest.mock import MagicMock def test_send_transfer_happy_path(): # 1. Arrange: Setup mock dependencies db = MagicMock() notifier = MagicMock() mock_recipient = MagicMock() mock_recipient.email = "test@example.com" db.find_account.return_value = mock_recipient # Canned response # 2. Act: Execute transfer result = send_transfer(500, "rec_123", db, notifier) # 3. Assert: Verify outcome & call interactions assert result == "transfer_complete" db.debit_sender.assert_called_once_with(500) db.credit_recipient.assert_called_once_with(mock_recipient, 500) notifier.send_email.assert_called_once_with("test@example.com", 500)

Task (b): Negative Path Test (2 Points)

Assert Not Called

Verifies safety: when db.find_account returns None, money must NOT move and no emails must be sent.

def test_send_transfer_recipient_not_found(): # 1. Arrange: Simulate missing recipient db = MagicMock() notifier = MagicMock() db.find_account.return_value = None # 2. Act: Execute transfer with bad ID result = send_transfer(500, "invalid_id", db, notifier) # 3. Assert: Must return error AND must NOT call financial mutations assert result == "recipient_not_found" db.debit_sender.assert_not_called() db.credit_recipient.assert_not_called() notifier.send_email.assert_not_called()

Q1 · COVERAGE SUBSUMPTION (3 P)

Guard clause `transfer(amount, target_exists, daily_limit)` analysis.

👁️ Model Answer Click to reveal

(a) Statement Coverage (1 P): 4 test cases. Each return statement is mutually exclusive, so hitting all statements requires triggering each return path.

(b) Branch Coverage (1 P): 4 test cases. All branches are guard clauses with early returns, so traversing all 3 True paths + 1 False fall-through covers all branches.

(c) Nuance (1 P): In this specific code, missing limit_exceeded means statement coverage is not 100% because that return statement was skipped. In general code, however, statement coverage misses unwritten else branches.

Q2 · MC/DC DECISION TABLE (4 P)

`if is_premium and (balance > 10000 or overdraft_enabled)`

👁️ Model Answer Click to reveal

(a) Minimum Tests (1 P): N + 1 = 3 + 1 = 4 test cases.

(b) Minimal Suite & Independence Pairs (2 P):

  • TC1 (T, T, F) & TC2 (F, T, F) → proves is_premium
  • TC1 (T, T, F) & TC3 (T, F, F) → proves balance > 10000
  • TC3 (T, F, F) & TC4 (T, F, T) → proves overdraft_enabled

(c) Condition Coverage Flaw (1 P): Condition coverage only verifies that individual conditions were evaluated to True and False at least once; it does not ensure that the condition actually determined the decision outcome.
