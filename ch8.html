8. BDD & Gherkin

Key concepts and techniques

🎯 Chapter 8 Core Mission: Behavior-Driven Development (BDD) & Gherkin Engineering

BDD bridges the communication gap between business stakeholders, developers, and QA using Specification by Example. Learn how to write precise, testable Gherkin Scenarios (Given/When/Then) and map natural language steps into robust backend automation.

1. The Core Grammar of a Robust Gherkin Scenario

A good Gherkin scenario answers four core questions with observable, measurable outcomes:

Given (Context)

Sets up the initial state (preconditions: user balance, target account exists).

When (Action)

The single specific trigger event executed by the actor (submitting a transfer).

Then (Outcome)

The observable test oracle (transfer rejected, status code 400).

And (Side-Effects)

Secondary state invariants (no money debited from account, audit log written).

⚠️ Exam Trap: Vague Oracles in Gherkin

Never accept steps like Then everything is correct or Then the page changed. These are un-automatable vanity steps! A real oracle must assert exact status, balance invariancy, or audit logging.

2. Mapping Gherkin Steps to Technical Automation

Gherkin Step Technical Implementation / Automation Setup
Given user has balance of 200000 cents Database INSERT or API fixture provisioning user account with 200,000 cents in DB ledger.
When transfer of 100001 cents is submitted HTTP POST request to /api/transfers with payload {"amount": 100001, "target": "acc_123"}.
Then transfer is rejected Assert HTTP response code is 400 Bad Request and error JSON equals "Amount exceeds limit".
And no money is debited from source account Database SELECT query asserting source balance remains exactly 200,000 cents.
