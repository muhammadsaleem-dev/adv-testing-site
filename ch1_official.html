🏛️ Official Q COMPLETENESS (4 P)

Source: CH01_AdvTest_02_SelfTest.pdf

You are given the following function specification: A payment gateway accepts a transaction amount (integer, in Euro cents).

  • Valid amounts are between 1 and 100,000 (inclusive).
  • The function returns "approved" or raises a ValueError.
  • A colleague writes exactly two test cases:
    • amount = 500 → "approved"
    • amount = 50000 → "approved"

Identify at least three significant gaps in this test suite and justify why each gap matters.

👁️ Model Answer & Rubric Click to reveal Suggested Answer

Suggested Answer:

The test suite has at least the following significant gaps:

1. No boundary values tested (1 P) The boundaries of the valid range — 1 (minimum), 100000 (maximum) — are not tested. Boundary values are the most likely locations for off-by-one errors (e.g., > instead of >= in the implementation). The given values (500, 50000) lie well inside the valid range and reveal nothing about boundary behaviour.

2. No invalid inputs tested (1 P) There are no test cases for values outside the valid range: 0, -1, 100001, or very large negative numbers. A correct implementation must raise a ValueError for these inputs, but the test suite provides no means to detect a missing or incorrectly placed guard.

3. No edge case for the minimum valid value (1 P) amount = 1 is the smallest valid input. Many implementations fail silently at the lower bound (e.g., treating 0 as valid, or raising an error for 1 instead). This case must be tested explicitly.

4. No test for non-integer or missing input (1 P, optional / bonus) The specification says "integer in Euro cents". Passing a float (0.5), a string ("abc"), or None should either be rejected by the type system or handled gracefully. The current suite does not probe this at all.

Examiner note: Award 1 P per clearly identified gap with a justification that references why the gap matters (i.e., what class of bug it would miss). Listing gaps without justification earns half credit.

🏛️ Official Q ISTQB TERMINOLOGY IN CONTEXT (3 P)

Source: CH01_AdvTest_02_SelfTest.pdf

A developer runs the FinCon application and notices that the account balance displayed on screen is always €10 higher than the value stored in the database.

  • After investigation, it turns out that a rounding function was applied twice due to a copy-paste mistake introduced six months ago.

Using precise ISTQB terminology, identify and explain the role of:

  • (a) the human action that started the chain
  • (b) the flaw in the code
  • (c) the observable wrong behaviour
👁️ Model Answer & Rubric Click to reveal Suggested Answer

Suggested Answer:

  • (a) Error (1 P): The human action — the developer copying the rounding function call and accidentally applying it twice — is an error (ISTQB: a human action that produces an incorrect result). The mistake was made at the point of writing the code, not at the point of execution.
  • (b) Defect / Bug (1 P): The incorrect code that remains in the system — the duplicated rounding call — is a defect (synonym: bug, fault). It is a flaw in the component that can cause the system to fail. The defect existed in the codebase for six months before it was observed.
  • (c) Failure (1 P): The observable wrong behaviour — the account balance displayed being consistently €10 higher than the database value — is a failure: a deviation of the system from its expected delivery or result. The failure is what the tester or user can actually observe and report.

Summary of the chain: Error (human mistake) → Defect (flaw in code) → Failure (observable wrong behaviour).

Examiner note: Deduct 0.5 P if the student conflates "defect" and "failure". Deduct 0.5 P if the human action is described as a "bug" rather than an "error". Full credit requires all three terms used correctly with a brief explanation of each.

🏛️ Official Q AI IN TEST DESIGN (4 P)

Source: CH01_AdvTest_02_SelfTest.pdf

You prompt an LLM with the full FinCon requirements document and ask it to generate a complete test suite for the login feature.

  • The model returns 20 test cases within seconds.

Perform the following tasks:

  • (a) Name two concrete risks of using these test cases directly without review.
  • (b) Describe a practical review step you would apply to each generated test case before including it in the test suite.
👁️ Model Answer & Rubric Click to reveal Suggested Answer

Suggested Answer:

(a) Two concrete risks (2 P, 1 P each):

  • Risk 1 — Hallucinated expected results: LLMs generate plausible-sounding output but may produce test cases where the expected result is wrong. For example, the model might assert that a login with an empty password returns "success" if the training data contains similar patterns. Using such a test directly would validate incorrect behaviour.
  • Risk 2 — Happy-path bias / missing edge cases: LLMs tend to generate test cases for the normal, successful path. Invalid inputs (empty username, SQL injection attempt, session token reuse, brute-force lockout) are systematically underrepresented. A test suite that passes all 20 AI-generated cases may still miss the most security-critical scenarios.

(Additional acceptable risks: circular testing — model mirrors the code rather than the spec; missing non-functional aspects such as response time; over-coverage of obvious cases while duplicating tests rather than diversifying.)

(b) Practical review step (2 P):

For each generated test case, the tester should verify independently — without looking at the implementation — whether the expected result stated in the test case is correct according to the specification (not the code).

🏛️ Official Q DEBUGGING VS. TESTING (3 P)

Source: CH01_AdvTest_02_SelfTest.pdf

A project manager tells the team:

  • "Our testers found the bug and fixed it — great work!"

Explain what is wrong with this statement using the ISTQB definitions covered in this session. What are the correct responsibilities of testing and development respectively?

👁️ Model Answer & Rubric Click to reveal Suggested Answer

Suggested Answer:

The statement conflates two distinct activities that ISTQB assigns to different roles:

  • Testing (1 P): Testing is the activity of finding failures — observing that the system's actual result deviates from the expected result. Testers design and execute test cases, observe failures, and report defects. Finding the bug (i.e., detecting the failure) is within the tester's responsibility.
  • Debugging (1 P): Debugging is "the process of finding, analyzing and removing the causes of failures in a component or system" (ISTQB). This is the responsibility of development, not testing. Developers locate the root cause (the defect in the code) and remove it.
  • Why the distinction matters (1 P): If testers fix code, the separation of concerns that makes quality assurance meaningful breaks down. A developer who also tests their own fix is subject to confirmation bias — they tend to write tests that confirm the fix works rather than tests that challenge it. The ISTQB model deliberately separates detection (testing) from removal (debugging) to preserve objectivity.

Corrected statement: "Our testers found a failure and reported the defect; our developers debugged and fixed it."

🏛️ Official Q DOCTEST DESIGN (4 P)

Source: CH01_AdvTest_02_SelfTest.pdf

Below is a Python function without any doctest:

def classify_triangle(a, b, c): if a == b == c: return "equilateral" elif a == b or b == c or a == c: return "isosceles" else: return "scalene"

Perform the following tasks:

  • (a) Write a doctest block that achieves meaningful coverage, including at least one boundary/invalid case.
  • (b) The function currently accepts classify_triangle(0, 0, 0) and returns "equilateral". Is this correct behaviour? Justify your answer and describe how you would handle it in both the function and the doctest.
👁️ Model Answer & Rubric Click to reveal Suggested Answer

Suggested Answer:

(a) Doctest block with meaningful coverage (2 P):

def classify_triangle(a, b, c): """ Valid triangle types: >>> classify_triangle(1, 1, 1) 'equilateral' >>> classify_triangle(3, 3, 4) 'isosceles' >>> classify_triangle(3, 4, 3) 'isosceles' >>> classify_triangle(4, 3, 3) 'isosceles' >>> classify_triangle(3, 4, 5) 'scalene' Degenerate / invalid inputs (assuming ValueError is raised): >>> classify_triangle(0, 0, 0) Traceback (most recent call last): ... ValueError: sides must be positive integers """

Minimum for full credit: at least one case per valid type, all three permutations of an isosceles triangle tested, and at least one invalid/boundary case.

(b) Analysis of classify_triangle(0, 0, 0) → "equilateral" (2 P):

Is this correct? No. (0.5 P)

A triangle with sides of length 0 does not exist geometrically. The specification of the original self-assessment exercise requires sides to be positive integers. Returning "equilateral" for (0, 0, 0) is incorrect behaviour — it silently accepts an invalid input.

How to fix the function (1 P): Add a guard at the top of the function that raises a ValueError if any side is ≤ 0, or if the three sides do not satisfy the triangle inequality (a + b > c and all permutations):

def classify_triangle(a, b, c): if a <= 0 or b <= 0 or c <= 0: raise ValueError("sides must be positive integers") if a + b <= c or a + c <= b or b + c <= a: raise ValueError("not a valid triangle") if a == b == c: return "equilateral"
